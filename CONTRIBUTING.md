# Contributing

Agent Behavior Evals Lab is a deterministic, local-first evaluator for agent
behavior. Contributions should preserve the project boundary: the lab is the
evaluator, and models, tools, OpenClaw, Hermes, Codex, local runtimes, and
customer agents are systems under test.

## Local Setup

Use Python 3.10 or newer.

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
python -m pip install ".[dev]"
```

Useful commands:

```bash
python3 scripts/dev.py test
python3 scripts/dev.py check
python3 scripts/dev.py lint
```

The full deterministic gate is:

```bash
python3 scripts/dev.py check
```

## Deterministic Gate Rules

The deterministic quality gate must not:

- call hosted model providers;
- call local models or Ollama;
- execute OpenClaw, Hermes, Codex, or any other live agent runtime;
- use credentials or private accounts;
- perform network collection;
- execute browser, email, payment, database, or production actions;
- read private traces, private memory, private workspaces, or raw customer logs.

Live or private evidence can exist only through explicitly opt-in workflows and
must be normalized, reviewed, and public-safe before entering committed
fixtures.

## Public-Safe Fixture Rules

Committed fixtures must be public-safe. Do not contribute:

- secrets, API keys, tokens, cookies, credentials, or private URLs;
- private runtime logs, hidden prompts, raw memory, private workspace paths, or
  customer data;
- unredacted private evidence;
- claims that a fixture proves production safety, compliance, or model quality
  beyond the declared evidence class.

If in doubt, keep raw material local and ignored, then add only a reviewed,
redacted derivative fixture.

## Generated Artifacts

Many reports, traces, ledgers, and snapshots are regenerated by
`python3 scripts/dev.py check`. When changing schemas, cases, validators,
reports, scorer behavior, or manifests, run the full gate and review generated
diffs carefully.

Generated artifacts should be committed only when they are an intentional part
of the change.

## Case Contributions

New public cases should include:

- stable case ID;
- category and risk area;
- expected behavior;
- severity;
- policy references;
- expected failure modes;
- public-safe prompt and notes;
- standards mapping when standards coverage is enabled.

Do not add private or customer-specific cases to the public repository.

## Commercial Boundary

The public repository contains the open-source evaluator core. Customer audit
templates, private trace workflows, proprietary case packs, paid dashboards,
enterprise exports, and private adapters belong in the private/pro repository.
